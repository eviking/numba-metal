The standing bar for this project: below 1.5x isn't worth the added complexity of a GPU kernel; above 2x is where Metal earns its place over plain parallel Numba.

What each benchmark actually computes

The same computation is run four ways — plain Python/NumPy, single-threaded Numba, parallel Numba, and Metal — and timed. Correctness is checked every time: a run only counts if all methods agree (within floating-point tolerance) on the answer.

Vector polynomial

out[i] = ((1.75a + 0.25b)² − ab) / (|b| + 1)

One arithmetic formula applied independently to every element of two input arrays — no data dependency between elements at all. About as GPU-friendly a shape as exists, and about as little work as one thread can do.

Why it loses: the formula is a handful of operations. Launching a GPU kernel, moving data over, and collecting the result costs more than just doing the arithmetic on the CPU — the work is too small to be worth the trip.

Mandelbrot

z ← z² + c, repeated until |z| > 2 or 100 tries

One GPU thread per pixel. Each thread repeats the same tiny calculation up to 100 times, stopping early the moment its pixel "escapes" — so neighboring threads can finish after wildly different numbers of steps depending on which part of the fractal they landed in.

Why it wins big: millions of independent pixels, each doing real repeated work, is exactly the shape a GPU's thousands of cores are built for — and the win grows with image size because there's more of that work to spread across cores.

Heat diffusion (nonlinear)

next[x,y] = cur[x,y] + Σ e^−(gradient/κ)² · gradient

A 2D grid of temperatures spreads out over time, the way heat does in a metal plate. Each point looks at its 4 neighbors, but — unlike simple heat spreading — how much heat flows depends on how sharp the temperature difference is (steep edges resist blurring; this is the same technique used to smooth photos without losing edges). Repeated 200 times.

Why it wins, and keeps winning at 100x the grid: a plain constant-weight version of this (see below) is bottlenecked on moving data in and out of memory, and Apple Silicon's GPU has no memory-speed advantage over its CPU — so it actually got worse at large sizes. Adding the per-point exponential math swapped the bottleneck to raw computation, which the GPU does have far more of.

Monte Carlo paths

price ← price · e^(drift + noise), 100 steps

Prices a stock option by simulating thousands of random possible futures for the stock price (geometric Brownian motion — the standard model), then averaging the payoff across all of them. One GPU thread simulates one full price path, step by step.

Why it's middling: 100 steps per path is enough repeated work to be worthwhile at large path counts, but not dramatically more than a CPU thread can also chew through — a moderate, size-dependent win rather than a lopsided one.

Pairwise distance

distance[i,j] = Σ (a[i,k] − b[j,k])²

Given two lists of points, compute the distance from every point in the first list to every point in the second — the core operation behind nearest-neighbor search, clustering, and recommendation systems. One GPU thread per (i, j) pair in the output grid.

Why it's middling: each thread does only a short inner loop (as many steps as a point has dimensions, here 8 or 16) — real work, but not enough to fully hide the cost of writing a huge output matrix back to memory.

Cyclist aerodynamics

drag = ½ρv²·CdA(torso, arms, head)

Computes aerodynamic drag for cyclists in different riding positions, using real relationships from wind-tunnel research. Run two ways: once as a single instantaneous calculation ("sweep"), and once integrated over a 200-segment simulated race course ("course energy") — same physics, 200x more arithmetic per rider in the second version.

Why one version wins and the other doesn't: this pair exists specifically to isolate the effect of "how much math per byte moved." The single-calculation version is too little work to be worth a GPU trip; stretching the exact same physics over a course provides enough real work per thread to win clearly.

Implied volatility

solve: BlackScholes(σ) = market price

Given an option's actual traded price, work backwards to find the volatility assumption the market is implying — done today, at scale, by every options trading desk. Uses Newton-Raphson iteration: repeatedly guess, check, and refine, stopping as soon as the guess is accurate enough (each option can take a different number of steps).

Why it's a good GPU fit despite being "just" a loop: a GPU thread can run its own loop for exactly as long as it personally needs — unlike a batch tensor operation, which must pad every option out to the slowest one's iteration count.

Asian option pricing

payoff = max(average(prices) − K, 0)

Like Monte Carlo paths above, but the option's payout depends on the AVERAGE price over the option's whole life, not just the price on the last day — a real contract type with no shortcut formula, genuinely priced by simulation in practice. 500 steps per path (5x more than the plain version), with a running average kept up to date every step.

Why it's the strongest win in the suite: 5x the arithmetic per path, same amount of data moved per path — the clearest case in this whole report of "more real math per byte" directly buying a bigger, size-independent GPU advantage.
